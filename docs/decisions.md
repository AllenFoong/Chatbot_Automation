# 决定记录

> 每条决定写明原因。推翻某条决定时，不删除原记录，新增一条并注明取代哪一条。
> 最后更新：2026-10-14

| # | 决定 | 原因 |
|---|---|---|
| D1 | **不反编译 GPiS**，只研究数据库结构 | 手上没有源代码；反编译通常违反 EULA；数据库是标准 SQL Server，足够用 |
| D2 | **不解密 `sa` 密码**，用 Windows 身份验证连接 | 没必要，也等于破解厂商保护 |
| D3 | **主机只做只读查询和 `COPY_ONLY` 备份，不做任何测试** | 主机是诊所每天营业的生产环境 |
| D4 | 在**开发电脑**上还原为 **`GPiS_Dev`**，所有测试都在它上面做 | 可以随便试，弄坏了重新还原即可 |
| D5 | 第一阶段对 GPiS **只读，不写入** | `AppointmentID` 不是自动编号（GPiS 很可能用 MAX+1），同时写入会冲突；`TimeSlot`、`Duration` 格式也还没摸清 |
| D6 | 预约流程：**AI 读空档 → 生成待确认请求 → 员工确认后手动录入 GPiS** | 避免重复预约和写入风险 |
| D7 | 将来集成用**专门的只读 SQL 账号**，只开放预约相关表，**绝不用 `sa`** | 最小权限原则 |
| D8 | **营业时间由本系统配置** | GPiS 的 `RefTimeSlot` 覆盖全天 24 小时，没有营业时间 |
| D9 | 本系统数据用 **PostgreSQL**（读写），GPiS 的 **SQL Server 只读** | 两个数据库职责分开 |
| D10 | 方案 A（数据层）和方案 B（AI 对话层）**合并**成上下两层，而不是二选一 | AI 需要真实空档；数据层需要对话入口 |
| D11 | 不为病人开发 Mobile App | WhatsApp 即可完成预约，App 只会增加步骤 |
| D12 | GPiS 参考文件放在单独的私有仓库 `AllenFoong/GPiS-reference`；上传前排除 `.7z`、`.mp4`、`.pdb`、`.Err` 日志、图标图片，config 里的密码先遮掉 | 和本项目分开；避免大文件和敏感资料 |
| D13 | `Tbl_User` 本系统**绝不读取** | 员工密码很可能明文保存 |
| D14 | 医生排班、午休、疗程规则（占几格、能否当第 3 人）、每格容量、假期都存在本系统的设置表（`doctor_schedules`、`services`、`clinic_closures` 等），员工可在 Admin Platform 修改；假期由**假期管理模块**维护（全国 + Johor 公共假期、农历新年多休的日子）（扩展 D8） | GPiS 没有这些设置；排班、疗程规则、假期每年都会变，不能写死在代码里 |
| D15 | 空档计算**宁可少推荐，也不重复预约**：状态不明的算占用；现有预约只有 Remarks 写了 `1 hour` 才当 1 hour（员工看情况决定）；AI 只在 `OR`、`S+P`、`F`、`RETAINER` 时用第 3 个名额（可用 `max_per_slot_for_ai` 关掉）；`OFF DAY` 以外的占位记录、可能要 1 hour 的疗程、implant / denture / RCT 的后续步骤转人工 | Remarks 是自由文字，无法可靠解析；推荐错了比少推荐更伤害诊所信誉 |
| D16 | 多步骤疗程（implant、denture、矫正、RCT）的后续预约**只推荐原来那位医生**的时段。矫正的后续预约（`OR`、`RETAINER`、`RB`）由 AI 处理；implant、denture、RCT 的后续步骤转人工 | 诊所规定同一疗程要同一位医生做完（W9）；矫正的后续预约每次内容固定、30 分钟，`OR` 每月都有、数量多，最适合交给 AI；implant、denture、RCT 的下一步是哪一步、什么时候能来（例如要等技工所）、要不要 1 hour，AI 判断不了 |
| D17 | **对话按 WhatsApp 号码分**（`wa_contacts` → `conversations`），预约请求才指向具体哪一位病人（`appointment_requests.customer_id`）；`customers.phone` 不唯一（取代 `architecture.md` 初稿的 `conversations.customer_id`） | 统计 B11：2,243 个号码对应多于一位病人；一段对话可能帮几位家人预约 |
| D18 | 本系统数据库用 **SQLAlchemy 2.0 + Alembic + psycopg 3**；表结构的每次修改都写成 migration（`backend/migrations/`），测试检查 migration 建出来的表和 `models.py` 一模一样 | 表结构有版本记录；开发电脑和将来的云端用同一个指令建出一样的表 |
| D19 | 规则尽量写成**数据库约束**（CHECK、UNIQUE）：时间在 30 分钟格上、每格上限 1–3、一个号码只有一段没结束的对话、同一条 WhatsApp 消息只存一次。`clinic_settings` 只有一行、每个设置一栏（不用 key-value 表） | 程序有 bug、两个请求同时到、员工在 Admin Platform 输入错的值时，数据库是最后一道防线；每个设置一栏才能有类型和范围检查 |
| D20 | 测试连**真正的 PostgreSQL**，不用 SQLite 代替；测试数据库名字必须以 `_test` 结尾（测试会清空它），测试不能连 `DATABASE_URL`；没有设置 `TEST_DATABASE_URL` 就跳过 | SQLite 和 PostgreSQL 的行为不同（partial index、时区、CHECK）；名字检查防止清空开发用的数据库 |
| D21 | `services.multi_step`（是 / 否）改成 `treatment_group`（`IMPLANT` / `DENTURE` / `ORTHO` / `RCT`） | `get_treatment_doctor` 要找"上一次**同类**疗程"的医生（W9），光有是 / 否不知道哪些代码是同一类 |
| D22 | 员工在 `BOT` 模式的对话里回复，**等于接手**（mode 改成 `HUMAN`），AI 不再回复 | 避免 AI 和员工同时回复同一位病人 |
| D23 | `messages` 不存 `direction`，由 `sender` 决定（`CUSTOMER` = 收到，`BOT` / `STAFF` = 发出）；WhatsApp 24 小时规则从 `messages` 算出来，不另外存一栏 | 同一件事只存一次，不会互相矛盾 |
| D24 | Admin Platform **画面用英文**，前端用 **React + TypeScript**；Phase 4 分两步：4a 后端 API，4b 网页 | 员工习惯 GPiS 和疗程代码的英文；TypeScript 打错栏位名字时编辑器会提醒；每一步小一点比较好测试 |
| D25 | 员工分 **ADMIN / STAFF**：STAFF 处理对话和预约请求；只有 ADMIN 能改排班、疗程、假期、请假、每格上限、员工账号；至少要留一个 active 的 ADMIN | 设置改错会影响所有病人的空档；最少权限原则 |
| D26 | 登录用**服务器端 session**：密码用 Argon2 加密；cookie 是 HttpOnly + SameSite=Strict、12 小时失效；数据库只存 token 的 SHA-256；员工停用、重设密码时，已登录的马上失效（不用 JWT） | 网页里有病人资料；HttpOnly 防 XSS 偷 token，SameSite 防 CSRF；服务器端 session 可以马上撤销，JWT 做不到 |
| D27 | 公共假期用 Python `holidays` 套件预填（马来西亚 + Johor），**只加没有的日子**；农历新年多休的日子由员工自己加 | 每年手动输入容易漏；回教节日是预估日期、诊所多休的日子套件不知道，所以导入后要员工核对 |
| D28 | 员工在 Admin Platform **回复病人**的功能等 Phase 5 接上 WhatsApp 才做 | 现在存一条"发出"的消息，病人其实收不到，会误导员工 |
| D29 | 网页和 `/api` 放在**同一个网址**：开发时用 Vite 的 proxy（`localhost:5173/api` → `127.0.0.1:8000`），上线时由同一个服务器提供 `dist/` 和 `/api`（Phase 7）；后端**不开 CORS** | 登录 cookie 是 `SameSite=Strict`（D26），不同网址的请求不会带上它；开 CORS 还要允许带 cookie，多一个设错就被别的网站利用的地方 |
| D30 | 前端只用 **React、React Router** 两个执行时套件：不用 UI 套件、状态管理或资料请求套件；版本固定在 `package-lock.json`，全部支持 Node 22.13 | 画面不多，自己写比较容易看懂、维护；套件越少，供应链风险越小，升级也少出问题 |
| D31 | 浏览器**不存任何资料**（不用 localStorage / sessionStorage）：登录状态每次问 `/api/auth/me`，任何 API 回 401 就回到登录画面；时间一律显示马来西亚时间（`Asia/Kuala_Lumpur`）。按角色隐藏按钮只是方便，**权限由后端决定** | 网页里有病人资料，诊所电脑可能多人共用；cookie 是 HttpOnly，JavaScript 本来就碰不到；前端的检查谁都能绕过，只有后端的检查算数 |
| D32 | 对话、请求用**定时重新读取**（对话 10 秒、列表 15 秒、选单数字 30 秒；分页不在前景时不读），不用 WebSocket | 员工人数少，这样最简单；Phase 5 接上 WhatsApp、消息变多时再评估要不要即时推送 |
| D33 | 牙冠、牙桥也算多步骤疗程：疗程类别加 `CROWN`（`SC` → `ISSUE CROWN`）、`BRIDGE`（`SCAN B` → `ISSUE BRIDGE`），后续的 `ISSUE` 只找原来那位医生、转人工（`ai_can_book` = 否）（扩展 D16、D21） | 都是分两次做、要同一位医生（W29）；戴上的日子要等牙冠 / 牙桥做好，和 implant、denture 一样 AI 判断不了 |
| D34 | Phase 5 开发**只用 Meta 的测试号码**，而且只发给 `WHATSAPP_ALLOWED_RECIPIENTS` 里的号码（没设定 = 谁都不能发；`*` = 谁都可以，只有上线才用）。检查放在最底层的发送函数。开发用的 Meta App 放在**自己建的测试 Business portfolio**，不放诊所的 | 规则 4：测试号码只能和自己登记的最多 5 个号码互传，真的病人碰不到；5b 会读 `GPiS_Dev` 里真的电话号码，就算程序有 bug 也不能发出去。和诊所的 portfolio 分开（像 `GPiS_Dev` 和主机分开）：诊所的号码以后接上 Cloud API 时，开发用的 App 碰不到真的病人消息；测试出错（例如被 Meta 限制）也不会连累诊所的帐号；用诊所的帐号要先有诊所同意（A5） |
| D35 | 收 webhook 的是**单独的小程序**（`app/webhook_main.py`，port 8001）：只有 `/webhook`、`/health`，没有 `/docs`，只连本系统的 PostgreSQL、不连 GPiS。开发时只把它经 tunnel（cloudflared）放上网 | Meta 要连到公开的 https 网址；Admin API、`/availability`（读 `GPiS_Dev`、不用登录）不能放上网。每个 webhook 都检查 Meta 的签名，不是 Meta 送来的不处理 |
| D36 | 员工回复：**先经 WhatsApp 发出，WhatsApp 收下了才存**；送达状态 `ACCEPTED → SENT → DELIVERED → READ` 只往前走，`FAILED` 存原因给员工看（实现 D28 等的功能） | D28 的顾虑：画面上的"发出"消息一定真的发出去了；送不到（例如超过 24 小时）要让员工知道，不能以为病人收到了 |
| D37 | 还没有 AI（`AI_REPLIES_ENABLED=false`）时，病人的新对话**直接交给员工**（`HUMAN`，写明原因）；转给员工、还没有人负责的对话，第一个回复的员工负责 | 不然对话停在 `BOT`，画面说"AI 在回复"，其实没有人回 |
| D38 | 病人传的照片、语音、文件**先不下载**，只存 `[Image]`、`[Voice message]` 等说明；程序日志也不记消息内容和电话号码 | 是病人资料（可能是伤口照片）；存在哪里、保留多久要先决定（A9）。日志常常被复制、贴出去，不能有病人资料 |
| D39 | 开发用的 WhatsApp access token 用**测试 Business portfolio 里 System User 的 token**：只给测试 App 和测试 WhatsApp 帐号、只有 `whatsapp_business_messaging` + `whatsapp_business_management`、**60 天**失效（不选 *Never*），只存在 `.env`；怀疑外泄就 *Revoke* | *API Setup* 按出来的 token 实测大约 1 小时就失效，测试清单做不完；60 天的 token 外泄了也会自己失效，权限只到测试号码（D34）。上线（5c）的 token 怎么保管，到时再决定 |

D40–D62 是 **Phase 5b（预约提醒）、A1 和 5c 的设计决定**，2026-10-08（设计见 [`architecture.md`](architecture.md) 第 8–10 节）。
D48–D50 是按诊所第一轮问卷、D51–D53 是按第二轮问卷（都是 2026-10-08）新增的；D48 取代 D42、D43 的一部分。D63 是开发电脑演练装电脑 B（2026-10-12）之后新增的。D64 是在诊所装电脑 B 第一天（2026-10-12）之后新增的。D67 是 A10（病人资料在本系统留多久，2026-10-13）。D68 是 5c 要不要接、怎么接（2026-10-14）。D69 是病人传了证件号码怎么处理（2026-10-14，Phase 6 设计）。D70 是员工在 GPiS 输入后，系统自动找到那个预约（2026-10-14，Phase 6 设计）。

| # | 决定 | 原因 |

| D40 | 提醒先做「**员工确认后按 Send**」：系统准备好名单，员工在 Admin Platform 看过、取消勾选例外，再按一次 Send；**全自动定时以后再做**（A1 解决、上线几星期员工几乎不用改名单之后），同一套程序，只是由定时器代替员工按 | GPiS 有占位记录、状态不明的记录，病人打电话取消了 GPiS 可能还没改；发错了收不回，一次可能错几十位病人。按一次 Send 已经比现在一条条手动发快很多。全自动还需要一台一直开着、读得到主机实时预约的机器（A1） |
| D41 | 提醒名单**沿用空档的规则**：空档计算里「算病人」的预约（排除 `Canceled`、`Postpone`、`00:00`、`OFFDAY` 占位）才提醒；诊所联系人、状态不明（空 / `Waiting` / `Rearrange`）、号码空或固网、那天是休息日 / 医生请假 / 医生已停用 → **不自动发，交给员工看**。同一个**标准化后的号码**、同一个预约日期的所有预约合成**一条**，每行写时间、病人名字、医生，不写疗程 | 同一套判断只写一次，改规则不会两边不一样；不确定的不发（和空档「宁可少推荐」一样的道理）。统计 B11：2,243 个号码有多于一位病人，一个号码收一条比较清楚；疗程是健康资料，Remarks 里还有别人的名字（B5） |
| D42 | 模板用 **Utility** 类别，只写预约资料、**不夹促销**；写**日期**不写 "tomorrow"；两个 quick reply 按钮（*Confirm*、*Reschedule*），footer 写怎么停止（`STOP`）；变量里不换行（家人的预约用 `; ` 写在同一行）；送审的范例只用假名字。开发时在测试 WABA 建，5c 在诊所的 WABA 再建、再送审 | 预约提醒是 Meta 的 utility 用途；夹了促销会变成 marketing（比较贵、病人比较会 block）。假期前要提早几天发，写「明天」会错。按钮让病人一按就回答，程序也知道回的是哪一条提醒。模板属于 WABA，不会跟着号码走 |
| D43 | 提醒存在**单独的 `reminders` 表**，发的时候**不开对话、不放进 `messages`**；病人回复才照常进 *Conversations*，用按钮的 payload、`context.id`、48 小时内同一个号码对上是哪一条提醒。按 *Confirm* → 记在提醒上，只为这个按钮开的对话自动结束；按 *Reschedule*、打字回复 → 交给员工；对话画面旁边显示这个号码最近的提醒 | 每天几十条提醒都开对话，员工分不出哪些要处理；*Confirm* 不用员工做任何事。员工看到回复时要知道病人在回哪一条提醒 |
| D44 | 提醒的**三道锁**：① `REMINDERS_MODE` 默认 `preview`（只看名单、没有 Send 按钮），明确写 `send` 才能发；② 预约从 `GPiS_Dev` 读的就**拒绝发送**，只有读主机的 `GPiS` 才能发；③ 新的 `send_template` 和 `send_text` 一样在最底层检查允许名单（D34）。开发时要真的发，用**假的预约来源**（Demo 名字 + 自己的手机）。给 AI 对照的终端输出只有 ID、时间、医生、状态、原因、号码代号，不印名字、号码、Remarks；`Remarks` 只在内存里判断 `OFFDAY`，不存、不发 | 规则 4：`GPiS_Dev` 里是真的病人名字和电话，就算程序有 bug、`.env` 设错一项，也不能发出去，所以三道锁互相独立。要测模板和按钮又不能碰真的资料，所以用假来源 |
| D45 | 发送**最多一次**：同一个号码、同一个预约日期只自动发一次（数据库 UNIQUE）；先写 `SENDING` 再调用 Meta，Meta 收下才记 wamid；中途断掉的显示 *Unknown*、**不自动重发**。按 Send 时后端**重新读 GPiS**，名单和员工看到的不一样就不发、请员工重看 | 病人收到两次提醒比漏一次更困扰，漏的员工可以补；按两次、两个员工同时按都不会重复（D19：数据库是最后一道防线）。员工看名单到按 Send 之间 GPiS 可能被改（W26） |
| D46 | **病人同意**：对真的病人发之前，诊所要有收同意的方式（登记表 / PDPA 通知写明诊所名字、用 WhatsApp 发提醒、经 Meta 传送、怎么停止）；本系统做**号码层级的 opt-out**（回 `STOP` 或员工标记，整个号码不再收提醒）。同意没解决之前，5b 只在测试号码 + 假资料上跑 | WhatsApp 的规定：主动发消息要先有 opt-in（写明商家名字），要能停止。PDPA：看牙医的时间可能算健康资料（敏感个人资料），要通知用途、交给谁（Meta），还有跨境传送的规定。诊所现在有没有同意还不知道（W40） |
| D47 | 系统先按**一间分行**设计：不加「分行」栏位，模板里的分行名写成固定文字；以后再开分行，要另外设计每间分行的医生、排班、WhatsApp 号码和 GPiS | W44：现在只有一间分行（以前的已经关了）；为用不到的功能加栏位和设定，只会让系统变复杂 |

## 数据安全规则（病人资料，受马来西亚 PDPA 保护）

- ❌ 不用 WhatsApp / Telegram / 邮件附件传备份
- ❌ 不把数据库、备份、病人记录放进 GitHub 或任何 AI 对话
- ✅ 传输前用 **7-Zip AES 加密**（勾选"加密文件名"），密码不和文件放在一起
- ✅ 网盘中转后**删除文件并清空回收站**；公司电脑上退出私人账号
- ✅ 云端测试一律用**假数据**
- ✅ WhatsApp 开发只用 Meta 的测试号码和自己的手机（D34）；程序日志不记消息内容和电话号码（D38）
- ✅ 预约提醒（5b）：读 `GPiS_Dev` 只能「只看名单」，不能发送；真的发只用假的预约来源（D44）
- ✅ 本系统的病人资料有期限（D67）：提醒过了预约日期 90 天就删掉、只留每天的数目；电脑 B 的备份最多留 30 天；浏览器不快取 `/api`
- ✅ 给 AI 看 GPiS 截图前，先遮住 Patient Name、HP No、NRIC、House No 等栏位（或者用 `GPiS_Dev` 的假数据截图）

### 记录：备份的传输方式

主机（公司网络）与开发电脑（家里网络）不在同一网络，远程控制工具 Parsec 不支持传文件。
