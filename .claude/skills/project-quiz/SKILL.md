# 项目测验（`/project-quiz`）

目的：测试用户对 Chatbot_Automation 的了解。重点不是背数字，而是知道**每个方案为什么这样选**、遇到情况时照项目的规则该怎么做。

用户在 `/project-quiz` 后面带的参数：$ARGUMENTS
（没有被替换成内容、或是空的，就当没有参数；用户在消息里说的也算。）

- 数字 → 题数（默认 10，最多 20）。
- 主题 → 只考那个主题，例：`安全`、`空档`、`5b`、`提醒`、`A1`、`5c`、`部署`、`D40-D67`。
- `简单` / `难` → 难度。
- 没有参数 → 整个项目、10 题、难度混合。

## 规则（先看）

1. **只读文件**：只用 Read / Grep / Glob 读仓库里的文件。不连任何数据库、不跑程序、不改文件、不 commit；测验结果不写进仓库。
2. **病人资料**（`CLAUDE.md` 规则 4）：题目和选项不放真的病人名字、号码；要举例就用 `DEMO PATIENT` 这类假名字。不出密码、IP、帐号密码内容的题目。
3. **每题都要有出处**：正确答案必须是文件里写明的（D 编号、规则、章节、W 问题的回答）。出完题回头再读一次出处，确认答案没错。
   决定被后来的决定取代或修改的（例：D48 取代 D42 的按钮、D61 修正 D27、D64 修改 D62 的 USB、D65 修改 W42 的对照试跑），以**最新的**为准；文件说得不清楚就换一题。
4. 用简体中文；文件里的英文名词、代码照原样写（`COPY_ONLY`、*Open in WhatsApp*、`*C`）。

## 第 1 步：读资料

一定要整份读：

- `CLAUDE.md`：规则 1–6、当前进度、下一步
- `docs/decisions.md`：D1 以后的每个决定和原因、数据安全规则（**出题的主要来源**）
- `docs/architecture.md`：第 1–7 节（需求、两层结构、技术选型、空档规则、人工介入、开发路线、未解决的问题 A1–A10）；第 8 节（5b 提醒）；第 9 节（A1 四个方案比较）；第 10 节（5c、第三方平台、Plan B）

按要考的主题再读（可以只读相关章节）：

- `docs/clinic-workflow.md`：营业时间、医生排班、每格容量、占位记录、`00:00`、Remarks 治疗代码、W 问题的回答
- `docs/gpis-database.md`：GPiS 的表、统计查询的结论（只用统计数字和结论）
- `sql/README.md`：空档 SQL、只读帐号
- `backend/README.md`、`frontend/README.md`：各 Phase 做了什么、怎么测
- `docs/deploy-pc-b.md`、`docs/pc-b-checklist.md`：装到电脑 B、演练、更新、备份、还原

文件里有新的 D 编号、新章节，也一样可以出题。

## 第 2 步：先出好全部题目（不要给用户看）

### 主题

考整个项目时：至少涵盖 6 个主题，每个主题最多 2 题。用户指定了主题，就只在那个主题里出（可以连到相关的 D）。

| 主题 | 可以考的（例） |
|---|---|

| 2. 安全和规则 | 规则 1–6 为什么存在；不反编译、不解密 `sa`、不读 `Tbl_User`（D1、D2、D13）；为什么在 `GPiS_Dev` 测试、主机只做 `COPY_ONLY` 备份（D3、D4）；数据安全规则（加密传输、网盘用完就删） |
| 3. 空档规则 | 「宁可少推荐，也不重复预约」（D15）；多步骤疗程只找原来的医生、哪些转人工（D16、D33）；占位记录、`00:00`、`1 hour`；营业时间、排班为什么由本系统设置（D8、D14） |

### 好题目的标准

- 问「**为什么**」或「**遇到这个情况，照项目的规则该怎么做**」。不考背的东西：测试个数、日期、PR 编号、port 号码、文件行数。
- 题型混合：
  - 原因题：「为什么……？」
  - 情境题：「员工按了 *Open in WhatsApp*，但 WhatsApp 打开后没有按 Enter，应该……？」
  - 取舍题：「和方案 1 比，方案 3 多了什么问题？」
  - 反向题（最多 2 题）：「下面哪一个**不是**……的原因？」，「不是」要加粗。
- 4 个选项 A–D，**只有一个对**。错的选项要像真的：用项目**考虑过但没选**的做法（JWT、测试用 SQLite、VPN 直连、装在主机 A、非官方 WhatsApp 工具、全自动定时发、把空档推上云端……）或常见的误解。不用一看就错、好笑的选项；不用「以上皆是 / 以上皆非」。
- 四个选项长度差不多，正确的那个不要特别长、特别详细。
- 正确答案的位置要分散：10 题里 A、B、C、D 各 2–3 次，不要连续 3 题同一个字母。
- 难度（没有指定时）：约 3 题简单（规则、整体方向）、5 题中等、2 题难（要把两三个决定连起来想，例：为什么 D44 的三道锁要互相独立）。
- 同一个 D 编号不出两题；用户「再来一轮」时，避开这次对话里已经考过的 D 编号。

每题自己记下（不显示）：题目、A–D、正确答案、一句「为什么对」、每个错的选项错在哪、出处（文件 + D 编号 / 章节）。

示例（只示范格式，不要原样拿来出题）：

> **题目**：为什么第一阶段本系统对 GPiS 只读、不直接把预约写进去？
> A. GPiS 的数据库有加密，外部程序写不进去
> B. `AppointmentID` 不是自动编号，同时写入会冲突，时段格式也还没摸清
> C. SQL Server Express 不接受从别的电脑写入
> D. 写进 GPiS 要先付开发商的授权费
> **答案**：B　**出处**：`docs/decisions.md` D5

不好的题目：「Phase 5a 合并时 `pytest` 有几个测试？」（背数字，和「为什么」无关）

## 第 3 步：一次问一题

开始前只说一行：「共 N 题，范围：……。每题选一个答案，选了马上告诉你对不对。」

每一题用 **AskUserQuestion** 问，一次只放一题、`multiSelect: false`：

- `question`：「第 3/10 题：……？」（完整的题目）
- `header`：「第 3/10 题」
- `options`：4 个，顺序就是 A–D。`label` 写「A. 」加上简短的选项；`description` 写完整的选项内容。
- **不要**在 label、description 里写「(Recommended)」、「推荐」或任何暗示答案的字。

用户回答后先判断：

- 选了 A–D → 对照答案。
- 选了 Other、自己打字：打的是一个字母，就当选那个选项；打的是自己的答案，按意思判断（意思和正确答案一样就算对）；「不知道」「跳过」算错；「结束」「stop」→ 直接到第 4 步。

然后显示结果。同一个回覆里，显示完结果就用 AskUserQuestion 问下一题。

答对：

```
✅ 答对了！（目前 3/3）
为什么：……（1–2 句）
出处：docs/decisions.md D26
```

答错：

```
❌ 答错了。（目前 2/3）
你选的：B. ……
正确答案：C. ……
为什么：……（2–3 句，讲清楚原因）
你选的为什么不对：……（1 句）
出处：docs/architecture.md 9.3
```

**没有 AskUserQuestion 工具时**（例：把这份提示词贴到 claude.ai、附上文件来用）：把题目和 A–D 打出来，最后写「请回复 A、B、C 或 D」，然后**停下来等用户回复**。同一个回覆里绝对不能出现答案或提示；收到回复后照上面的格式显示结果，再出下一题。

## 第 4 步：成绩单

全部答完（或用户说结束）后：

```
## 成绩：7 / 10（70%）

| # | 主题 | 你的答案 | 正确答案 | |
|---|---|---|---|---|
| 1 | 整体方向（D5） | B | B | ✅ |
| 2 | 预约提醒（D44） | A | C | ❌ |
```

评语：

- 9–10 题对：对项目的取舍很清楚，可以向别人解释为什么这样做。
- 7–8 题对：大方向懂了，有几个细节要再看。
- 5–6 题对：知道做了什么，但「为什么」还不熟。
- 0–4 题对：建议先读 `CLAUDE.md` 和 `docs/decisions.md` 再来。

（题数不是 10 时照比例套用：90% 以上、70%、50%、50% 以下。）

答错的题目按主题列出「建议再读」的文件和章节（例：`docs/decisions.md` D40–D45、`docs/architecture.md` 8.4）。

最后用 AskUserQuestion 问要不要继续，选项：「再来一轮（换题）」、「只考答错的主题」、「结束」。
